# Operating Model

本文档定义 `mac-cleanup` 的核心运作准则与知识管理机制。

## 一、核心工作流

每一次存储治理周期均严格遵循五步闭环：

```
Observe (重新探测) → Diagnose (多维诊断) → Cleanup / Organize (决策执行) → Verify (实证复验) → Promote (规则沉淀)
```

1. **重新探测（Observe）**：每次操作前必须全量采集最新的容量与目录状态，不依赖历史记忆；
2. **多维诊断（Diagnose）**：结合硬件约束、工作负载与异常特征，生成本轮的动态候选名单；
3. **决策执行（Cleanup / Organize）**：根据风险等级与用户授权，精准实施清理或归属重构；
4. **实证复验（Verify）**：执行后立即重新测量容量与应用行为，确认操作有效性与系统稳定性；
5. **规则沉淀（Promote）**：将经过检验的安全规律与治理模式晋升为可复用规范，淘汰临时推论。

---

## 二、十项操作准则（Ten Principles）

1. **每轮状态必须重新探测**：系统是动态演变的，禁止跨会话套用过期测量值。
2. **不假设历史瓶颈恒定**：上轮最大的空间消耗项，本轮可能已被释放或被新产生的数据覆盖。
3. **治理目标动态决策**：根据当前最紧迫的瓶颈（如日常运行受阻 vs 系统更新就绪）确定治理优先级。
4. **严格的三级风险防护**：所有候选目标必须明确分类为 `LOW RISK`、`REVIEW FIRST` 或 `HIGH RISK`。
5. **用户真实数据默认不可自动删除**：包含工作文档、聊天数据库、真实代码及多媒体资产等一律列为最高防护级别。
6. **文件“归属整理”等同于清理**：将零散文件重命名、归档到外部存储或移至规范目录，是减少系统盘压力的一等公民操作。
7. **开发环境梳理等同于清理**：识别并清除废弃虚拟环境、孤儿依赖与重复运行时，与删除无用文件具有同等地位。
8. **执行前必留基线（Baseline）**：无基线不执行，确保任何清理带来的增益均可量化对比。
9. **执行后必做实证测量（Verify）**：严谨对比前后容量差值，并验证关键软件（如系统应用、通信工具）的连通性与健康状态。
10. **仅凭证据支持晋升通用规则**：杜绝“直觉式清理”，任何经验只有在经历完整“假设 → 执行 → 验证”闭环后方可转化为项目规则。

## 三、知识晋升体系（Knowledge Promotion）

为了防止一次性的波动数据污染项目规范，每一轮交互的产物必须严格归入以下四个层次：

```
[Dynamic Snapshot] (临时测量值 / 本地隔离)
         ↓ 经时间与架构复核
[Stable Machine Fact] (机器相对稳定的客观特性)

[Cleanup Hypothesis] (治理假设 / 本地试验)
         ↓ 经清理执行与连通性验证
[Validated Cleanup Rule] (可无风险重复使用的清理规则)

[Governance Observation] (环境生态发现)
         ↓ 经规范化权衡
[Organization / Environment Policy Candidate] (环境治理策略候选)
```

### 1. Dynamic Snapshot（动态快照）
- **定义**：某一时刻对机器存储状态的只读切片（如特定时刻的具体空闲字节数、特定目录的临时体积）。
- **生命周期**：仅存在于 `local/snapshots/`，易失、严禁 commit 到公共代码仓库。
- **原则**：绝不把“某目录当前占用了 7.6GB”这类数值作为持久规则沉淀。

### 2. Stable Machine Fact（稳定机器画像）
- **定义**：设备长期稳定、低频变化的物理配置与架构事实（如芯片架构、物理磁盘标称等级、主工作负载类型）。
- **维护位置**：`docs/machine-profile.md`。
- **原则**：只记录去隐私化的客观事实，并显式标注 `Last verified`。

### 3. Validated Cleanup Rule（已验证清理规则）
- **定义**：经过实际清理操作、容量实测核对，并验证对应软件运行正常的完全安全、可重复的清理手段。
- **晋升条件**：必须包含因果证明（执行前大小 → 清理命令 → 释放大小 → 应用功能无损）。

### 4. Organization / Environment Policy Candidate（环境治理策略候选）
- **定义**：针对多运行时、多包管理器或混乱工作区的结构性治理策略建议，供用户确认后落地为长期工程规范。

## 四、开发与运行环境长期治理方向（Policy Candidates）

针对当前机器的多套工具链共存现状，以下事项已正式立项为长期治理课题（暂不盲目删除，等待后续专项评估）：

1. **多 Conda / Python Runtime 真实冗余排查**：
   - 厘清系统是否存在由 RStudio、系统全局、Miniconda、用户环境引发的多套 Python 重复实例；
   - 评估多环境独立隔离（Project Isolation）与磁盘空间倍增（Disk Duplication）之间的合理平衡点。
2. **各语言生态的 Canonical Manager 选型收敛**：
   - 避免随波逐流选择框架，根据日常工作负载（科研教学 + Agent 开发），为 Python、Node 等明确唯一的标准包管理器与缓存策略。
3. **防范 CLI 工具多渠道重复安装**：
   - 建立检查机制，避免同一个 CLI（如 ffmpeg、yt-dlp、pandoc 等）同时出现在 Homebrew、pip、npm 和手动编译路径中。
4. **包管理全局缓存自动化回收策略**：
   - 建立定期修剪 `uv`、`pip`、`npm`、`Homebrew` 历史下载 wheel/tarball 缓存的标准动作。
5. **孤儿项目与废弃虚拟环境识别**：
   - 建立机制扫描长期未触碰的代码仓库中庞大的 `node_modules` 与 `.venv` 并实施休眠或删除。
